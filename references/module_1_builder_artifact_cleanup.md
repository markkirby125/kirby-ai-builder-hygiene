# Module 1: Builder Artifact Cleanup

Removes the debug attributes, generator comments, meta tags and dev tooling that AI visual builders (Lovable, v0, Bolt, Cursor scaffolds) leave in exported code. The goal is code hygiene: smaller markup, fewer stray attributes, and nothing in the repo that only the builder's editor reads. This module changes no layout, styling or behaviour. Run it first; [Module 2](./module_2_semantic_dom_flattening.md) runs next.

## 1.1 When to run

- The repo is a builder export, or the user asks to clean one. A repo qualifies when this detection grep, run from its root, prints at least one file. This is the copy of record; [Module 5](./module_5_handoffs.md) points here.

```bash
grep -rIil --exclude-dir={node_modules,.git,dist,build,.next,out,coverage,.wrangler,.vercel,.netlify} \
  -e 'data-lovable-' -e 'data-v0-' -e 'data-bolt-' -e 'lovable-tagger' \
  -e 'data-source-\(line\|file\)' -e 'generated by \(lovable\|v0\|bolt\)' -e 'v0-container' -e '__v0' \
  -e 'name="generator" content="[^"]*\(lovable\|v0\|bolt\|cursor\)' .
```

The generator pattern matches only builder generator tags, so a plain Next.js, Astro, Gatsby or Hugo generator meta does not qualify a repo. `__ai` is left out of this grep on purpose: it is too generic to qualify a repo on its own (see 1.2). The `{...}` brace expansion needs bash or zsh (see section 1.4 step 2). The dispatcher runs this grep first (step D). If it prints nothing, the skill does not apply: report `not applicable` and stop unless the user insists.
- Preconditions (in analysis-only mode, see the [dispatcher](./00_dispatcher.md) Modes: skip preconditions 1 and 2 and the edit, install and checkpoint steps (4, 5, 8 and 9); edit, commit, install and capture nothing; run the detection and inventory greps and steps 3, 6 and 7, and list proposed changes):
  1. `git rev-parse --verify HEAD` succeeds and `git status --short -- .`, run from the package root (the folder that holds the exported app), prints nothing. Tracked files that a project hook rewrites (for example a stamped sitemap) may be left out of this check only with the user's approval; list them. Otherwise stop before any edit and ask the user. Never commit without their approval. This covers the baseline and `wip:` commits only; checkpoint commits are approved once in step 9.
     - No repo or no commit: with approval, agree a `.gitignore` first (`node_modules`, build output, `.env*`), run `git init`, show `git status --short`, then stage the agreed files by explicit path and make one baseline commit: `git commit -m "baseline: untouched export"`.
     - Dirty tree: with approval, commit the user's changes first and separately, staged by the explicit paths they confirm: `git commit -m "wip: changes before builder cleanup"`. The `m1` checkpoint is the next commit. Never fold user edits into a cleanup commit.

     If the project's rules set a commit-message format, write both messages in it and keep the `baseline:` or `wip:` tag (dispatcher locked decision 8).

     In every case, before the first edit, record the pre-cleanup baseline sha with `git rev-parse --short HEAD` and keep it as `<baseline-sha>`. [Module 4](./module_4_verification.md) uses it.
  2. The project's build and test commands are known, the user has confirmed the command list (dispatcher, Inputs), and their current result is recorded before any edit; [Module 4](./module_4_verification.md) compares against this baseline. A failure that exists before the edit is recorded as the baseline and is not fixed in this module.
  3. You know which builder produced the code. Check `package.json`, the vite or next config, and the first lines of the main layout file.

## 1.2 Artifact catalogue

| Pattern | Where it appears | Action |
|---|---|---|
| `data-lovable-*`, `data-v0-*`, `data-bolt-*` | JSX/TSX/HTML elements | Remove |
| `data-source-line`, `data-source-file` | Elements, injected by dev plugins | Remove |
| `__v0*`, `__ai*` attributes or props | Elements, component props | Remove after a grep shows no reader. `__ai*` is too generic to qualify a repo on its own; treat it as an artifact only in a repo that step D already qualified |
| `data-component-*` | Elements | Grep first (1.3); remove only with zero readers |
| `data-id` | Elements | Grep first (1.3); remove only with zero readers |
| `lovable-tagger` | `vite.config.*` plugins, `package.json` devDependencies | Remove the plugin call and the dependency together |
| Generator comments that name a builder ("Generated by Lovable", "Generated by v0", "v0-container") | Top of files, around blocks | Remove. Leave other tools' headers, such as Wrangler typegen's "Generated by Wrangler" or codegen banners |
| `<meta name="generator">` from a builder | `index.html`, layout head | Remove |
| Builder preview or debug scripts, inspector hooks, builder CDN debug references | `index.html`, layout head, entry file | Remove; if unsure, list it under "Uncertain" (1.8). If a builder-injected script sends analytics, sets cookies or loads a consent banner, it counts as analytics or consent: keep it and list it |
| Analytics, tag manager, consent scripts (GA4, GTM, Plausible, consent banners) | Head, layout, entry file | Keep. Never remove |
| CAPTCHA or bot protection (Turnstile, reCAPTCHA, hCaptcha); vendored third-party widgets (chat, booking, maps, payment embeds) | Head, forms, layout, vendor folders | Keep. Never remove; list them as kept |
| `data-state`, `data-slot`, `data-orientation`, `data-side`, `data-align`, `data-radix-*`, `data-testid` | shadcn, Radix, other UI libraries, the project's own scripts, test runners; Tailwind variants such as `data-[state=open]:` style them | Never remove |
| Builder badge or attribution ("Made with Lovable", "Edit in v0") | Footer, floating corner element, injected script | Flag in the report. Never remove silently |

## 1.3 Grep-before-delete rule

`data-id`, `data-component-*`, `__v0*` and `__ai*` may be read by tests, CSS or JS. For each distinct attribute or prop name, run:

```bash
grep -rInE --exclude-dir={node_modules,.git,dist,build,.next,out,coverage,.wrangler,.vercel,.netlify} \
  -e 'data-id' -e "dataset(\s|\.|\[)\s*['\"]?id" -e "getAttribute\(\s*['\"]data-id" .
```

Swap in each `data-component-<name>` and its camelCase `component<Name>` dataset key. For each `__v0*` or `__ai*` name, grep the exact name with the same excludes (`grep -rIn --exclude-dir={node_modules,.git,dist,build,.next,out,coverage,.wrangler,.vercel,.netlify} -e '<name>' .`). Ignore hits on the element that carries the attribute; any other hit (a selector, a `querySelector`, a test, a `dataset` or `getAttribute` read) keeps the attribute. Put it on the "left in place" list with the file and line that reads it.

## 1.4 Procedure

If the head, layout or chrome is injected from partials or the assets are fingerprinted, follow the dispatcher's "Generated regions and asset pipelines" section: edit the source partial, regenerate, and run its `--check`.

1. Run the detection grep and record the hit list.
2. Inventory every artifact from the 1.2 catalogue with `grep -rIn` and the excludes below. Save the counts per pattern. For builder attributes, use exactly the command that [Module 4](./module_4_verification.md) section 4 reruns:

   ```bash
   grep -rIn -e 'data-lovable-' -e 'data-v0-' -e 'data-bolt-' -e 'lovable-tagger' -e 'data-source-line' -e 'data-source-file' -e '__v0' -e 'v0-container' -ie 'generated by \(lovable\|v0\|bolt\)' --exclude-dir={node_modules,.git,dist,build,.next,out,coverage,.wrangler,.vercel,.netlify} .
   ```

   The `{...}` brace expansion needs bash or zsh. In another shell, write one `--exclude-dir=` per directory.

3. Apply the grep-before-delete rule to every `data-id`, `data-component-*`, `__v0*` and `__ai*` name.
4. Remove the confirmed artifacts. Edit files in place; do not reformat untouched lines.
5. If you removed `lovable-tagger`, delete its import and its entry in the `plugins` array, then run the package manager's uninstall: `npm uninstall lovable-tagger`, `pnpm remove lovable-tagger`, `yarn remove lovable-tagger` or `bun remove lovable-tagger`. Never hand-edit the lockfile.
6. Search the head and entry files for third-party scripts, and follow any runtime loader (a script that injects other `<script>` tags, a tag manager container, a partial or include script) to the tags it adds later. Record the pre-edit count of kept scripts and widgets for 1.7. Sort each one into keep (analytics, tag manager, consent, CAPTCHA, vendored widgets), remove (builder debug tooling) or uncertain.
7. Search for badges and attribution. Record each one with its file and line. Do not edit it.
8. Rerun the inventory greps. Every removed pattern must now return zero hits, including the generator meta check in [Module 4](./module_4_verification.md) section 4.
9. Run the build and tests and compare them with the baseline. Show the user the Module 1 diff. Then ask once whether they approve local checkpoint commits for the rest of the run, including the `git revert` commits Module 2 step 7 may need, and record the answer. With a yes, make the `m1` checkpoint (at the end of this module or at the start of Module 2, before its first component) only if this module changed a file; a zero-hit or analysis-only run changed none, so make no `m1` commit and record the current short sha as the revert base instead. Make every `m2` checkpoint without asking again. With a no, make no checkpoint commits. Tell the user that Module 2 needs checkpoint commits to roll back safely, and let them choose: approve the checkpoint commits, make each checkpoint commit by hand when you reach it, or skip Module 2. If they skip it, modules 3 and 4 run on the Module 1 result. Every checkpoint in this skill uses these steps:
   - List every path the step touched, new files included (`package.json` and the lockfile if step 5 ran).
   - Stage exactly those paths: `git add -- <path> [<path>...]`. Never use `git add -A`, `git add .` or `git commit -am`. Never stage `.env*`, key files or anything git ignores.
   - Run `git status --short` and confirm the staged set equals the touched set. Leave out any untracked file that is not ours and mention it to the user.
   - Commit with a unique message: `git commit -m "m1: builder artifact cleanup"` here, `m2: <component> (<n>)` in Module 2, `m3: utility class consolidation` in Module 3. If the project's rules set a commit-message format, follow it and keep the `m1`, `m2` or `m3` tag in the message (dispatcher locked decision 8). Never push or deploy.
   - Record the short sha (`git rev-parse --short HEAD`) for Module 2 step 7's revert range and the report. Checkpoint commits are local; the user may squash them. Then hand off to Module 2, or to Module 3 if Module 2 is skipped.

## 1.5 Prompt block

```text
You are cleaning HTML/JSX/TSX exported from an AI visual builder. This is code hygiene. Do not change layout, styling or behaviour.

Remove:
- Tool-injected attributes: data-lovable-*, data-v0-*, data-bolt-*, data-source-line, data-source-file.
- data-component-*, data-id, __v0* and __ai*, but only after a repo-wide grep shows nothing reads them (tests, CSS selectors, querySelector, dataset or getAttribute reads, props read by code).
- Builder comments such as "Generated by v0" or "v0-container". Leave other tools' generated headers.
- Builder generator <meta> tags.
- Builder debug scripts, inspector hooks, preview CDN references and the lovable-tagger dev plugin.

Keep:
- Event handlers, props, aria-* attributes and all styling.
- data-state, data-slot, data-orientation, data-side, data-align, data-radix-* and data-testid.
- All analytics, tag manager and consent scripts, CAPTCHA or bot protection, and vendored third-party widgets.
- Builder badges or attribution text. Flag them; do not remove them.

If you are not sure an item is builder-only, leave it and list it.

Output: a unified diff, then a report listing removed categories with counts, items left in place with the reason and the file:line that reads them, uncertain items, and flagged badges.
```

## 1.6 Do and do not

Do:
- Grep before every `data-id` and `data-component-*` removal.
- Keep analytics, tag manager and consent scripts, even if a builder injected them.
- List anything uncertain instead of deleting it.

Do not:
- Strip a builder badge or attribution. The plan terms may require it; the user decides.
- Touch `aria-*`, `role`, `id` used by labels, or any class name.
- Remove `data-state`, `data-slot`, `data-orientation`, `data-side`, `data-align`, `data-radix-*` or `data-testid`. shadcn, Radix, Tailwind `data-[...]:` variants and tests depend on them.
- Reformat files or reorder imports while you clean.

## 1.7 Verification

- Every removed pattern returns zero hits on a rerun of its grep.
- Every kept `data-id`, `data-component-*`, `__v0*` or `__ai*` has a recorded reader.
- The count of analytics, consent, CAPTCHA and vendored widget scripts matches the pre-edit count.
- The badge count matches the pre-edit count.
- Build and tests match the baseline result. Full checks run in [Module 4](./module_4_verification.md).
